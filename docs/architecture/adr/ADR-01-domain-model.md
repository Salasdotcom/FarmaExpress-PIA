# ADR-01. Selección del patrón Domain Model

| Campo del ADR | Contenido |
| --- | --- |
| Título | Selección del patrón Domain Model para la lógica de negocio de FarmaExpress. |
| Estado | Aceptado. |
| Contexto | FarmaExpress requiere administrar procesos relacionados con ventas, recetas, inventario, caducidad, retiros de lotes, ajustes de inventario y solicitudes de compra. Estos procesos contienen reglas de negocio que deben cumplirse para mantener la integridad de la información. Por ejemplo, impedir la venta de medicamentos caducados, controlar las modificaciones de ventas completadas y separar la autorización de un ajuste de su aplicación. Por lo tanto, se necesita una estructura que permita concentrar y mantener estas reglas de manera organizada. |
| Alternativas | **Transaction  Script:** implementar la lógica de cada operación mediante procedimientos independientes. Facilita el desarrollo inicial, pero puede provocar duplicación de reglas cuando diferentes operaciones necesitan las mismas validaciones. **Table Module:** organizar la lógica mediante módulos asociados a las tablas de la base de datos. Puede resultar sencillo para operaciones centradas en datos, pero ofrece menor representación de las entidades y reglas del negocio. **Domain Model:** representar los conceptos del negocio mediante clases que contienen datos, comportamientos y reglas. Requiere mayor diseño inicial, pero permite organizar las responsabilidades y mantener las reglas cerca de los elementos que las representan. |
| Decisión | Se propone utilizar el patrón **Domain Model**, porque FarmaExpress tiene reglas de negocio relacionadas entre sí que deben mantenerse consistentes. Este patrón permite representar conceptos como Venta, Existencia, RetiroDeLote, DiferenciaDeInventario, AjusteDeInventario y SolicitudDeCompra, además de concentrar las validaciones correspondientes en el dominio. |
| Consecuencias | **Beneficios:** mejor organización de las reglas de negocio, separación de responsabilidades y mayor facilidad para mantener y ampliar el sistema. **Costos:** requiere definir las entidades, sus relaciones, responsabilidades y reglas antes de implementar las operaciones. **Riesgos:** un diseño excesivamente complejo puede dificultar el mantenimiento. **Trabajo posterior:** completar el modelo de clases, definir los servicios de aplicación, repositorios y mecanismos de persistencia. |
| Trazabilidad | US01 (clasificación de caducidad), US02 (bloqueo de venta de medicamentos caducados), US03 (retiro de lotes), US09 (revisión de recetas), US13 (modificación y cancelación de ventas en proceso), US14 (corrección de ventas completadas), US15 (diferencias de inventario), US16 (investigación de diferencias) y US17 (ajustes de inventario). |
